# Report data folder

The renderer reads either a folder or one JSON file.

- Folder: `inputs.json` plus `responses/*.json`, read in file name order.
- File: `{"inputs": {...}, "responses": [...]}` with the same content. The test fixture `tests/fixtures/northwind.json` uses this form.

## responses

Each response is one tool call, copied unchanged:

```json
{"tool": "list_control_members", "arguments": {"control_id": "…", "limit": 100}, "response": {…}}
```

| Tool | Fields the renderer reads |
|---|---|
| `get_access_review_evidence` | `kept_direct_shares_as_of`; `controls[]`: `control_id`, `name`, `status`, `folders`, `approvals[]` (`at`, `carried_into_range`, `actor.type`, `actor.name`, `actor.surface`, `actor.assistant_client`), `kept_direct_shares[]` (`person`, `email`, `item_kind`, `item`, `role`), `removals[]` (`source`, `action`, `step`, `target_kind`, `target`, `principal`, `role`, `link_scope`, `state`, `at`, `reason`; a removal record has `grantee_kind` for `target_kind`, `result` (`removed`, `failed` or `pending`) for `state`, `confirmed_at`, and may have `role`, or `from_role` and `to_role` for a lowering, shown as "Edit → Read") |
| `get_control` | `control`: `id`, `provider`, `purpose`, `reason`, `folders[].site`, `folder_count` (more than the listed `folders` marks the site list incomplete), `kept_groups[]` and `dropped_groups[]` (`name`, `email`, `role`, `people_count`, `membership_incomplete`, `external_recipients`) |
| `list_control_members` | `control_id`; `members[]`: `id`, `name`, `email`, `title`, `department`, `role`, `is_owner`, `keeps_access`, `through_groups`, `individual_access`, `provenance` (`by`, `by_name`, `at`, `last_action`); and, once the tool returns them, `basis` and `account_type` |
| `get_control_activity` | `control_id`; `entries[]`: `at`, `type`. Changes in period counts the entries inside the period whose `type` the audit trail lists: `proposal_approved`, `proposal_reopened`, `proposal_superseded`, `member_added`, `member_removed`, `role_changed`, `made_owner`, `group_kept`, `group_dropped`, `plan_applied`, `plan_partially_applied` |
| `start_access_review_extract` | `extract_id`, `status`, `from`, `to` |
| `get_access_review_extract` | `extract_id`, `status` (`running`, `completed` or `failed`), `from`, `to`, `failure_reason`; once completed: `as_of`, `file` (`reference`, `sha256`, `bytes`, `format`), `controls`, `folders_read`, `rows`, `rows_by_kind`, `groups[]` (`name`, `kind` (`entra_group`, `sharepoint_group` or `google_group`), `counted_members`, `provider_member_count`, `nested_groups_match` (Google groups only: whether every group nested in it matched its own count too)), `exclusions[]` (`control_id`, `subject`, `reason`), `next_offset` (groups and exclusions share one offset, 25 of each per page) |
| `read_access_review_extract_rows` | `extract_id`, `status`, `sha256`, `next_cursor`, `sha256_verified` (cursor 0 only); `rows[]`: `control_name`, `folder`, `row_kind`, `grantee_type`, `principal_name`, `principal_email`, `login_name`, `roles`, `inherited`, `via_group_name`, `via_sharepoint_group_name`, `link_scope`, `link_type`, `link_expires_at`, `granted_on`, `group_owners_only`, `recipients_sampled`, `recipient_total_count`, `permission_id`, `principal_id`, `control_id`, `folder_item_id`, `drive_id`, `as_of` |

A response with `"refused": true` stops the render with its reason.

The render also stops, naming what is missing, when:

- a paged call stops early: a `next_offset` (evidence, members) or `next_cursor` (activity) has no response with that `offset` or `cursor` in its `arguments`. Activity may stop at a page whose oldest entry is older than the period start;
- the evidence date ranges (`arguments.from` and `arguments.to`) leave part of the review period out, or reach outside it;
- a control in the evidence has no `get_control`, `list_control_members` or `get_control_activity` response;
- the extract is still running: its last `start_access_review_extract` or `get_access_review_extract` response says `running`;
- the extract's days reach outside the review period;
- a completed extract misses a `get_access_review_extract` page (`offset` to `next_offset` from 0) or a `read_access_review_extract_rows` page (`cursor` to `next_cursor` from 0).

The extract: the render uses the extract named in the last extract response, by file order. With none, the report marks it "Not available in this version". A failed extract is shown as failed with its `failure_reason`, and the rest of the report renders. A completed extract fills Section 3 and Attachment F. The render does not refuse, but says plainly in Section 3, when a group's `counted_members` differs from its `provider_member_count` or a Google group's `nested_groups_match` is false, when the rows read differ from `rows` or `rows_by_kind`, when a rows page names another SHA-256 than `file.sha256`, or when `sha256_verified` is false.

No folder sets: when the evidence lists no control, the report still renders. Section 1 and the first line of the summary block say once that Polar Sky recorded no folder sets with an access approval in force in the period, so there was no access to review; the rows that depend on folder sets say "No folder sets", "No members", "No removals" and so on, and the figure cards and the outcome chart are left out.

When an approval ended: the first `get_control_activity` entry of type `proposal_reopened` (withdrawn), `proposal_superseded` (replaced by a later approval) or `proposal_dismissed` (rejected) after the approval, before the control's next approval and before the period ends, as the evidence tool decides which approvals were in force. The report calls each control a folder set. A control whose last approval in the evidence ended this way is counted as "approved, then withdrawn" (a person withdrew the approval and the folder set went back to awaiting review; or replaced by a later approval, or rejected), not as approved; its row says, for example, "Approved 2026-08-04, withdrawn 2026-10-19", and its members who keep access say "Yes, approved only until the approval was withdrawn 2026-10-19". A member whose `provenance.at` is after the end was decided later, so the report says, for example, "Added or changed 2026-10-25, after the approval was withdrawn 2026-10-19", and does not count them as having kept access while it was approved.

Approver type: an approval whose `actor.type` is `system` was made by Polar Sky itself, not by a person. The `approver_type` column says Person or Polar Sky; only people are counted as approvers. A folder set has an approval by a person in force at the period end when its latest approval is by a person and did not end in the period; the summary, the "Access authorized by a named person" row and `render_report.py --check` name the folder sets without one (approved by Polar Sky, or the approval ended), with each one's data owner (the member with `is_owner`), and the review interval check uses that approval's date.

Several frameworks: with more than one key in `frameworks`, the cover, the report details and Section 2 name every chosen framework, each with its requirement text, and use the generic words "in-scope data", the framework names in "Prepared for" (unless `prepared_for` is given), and the frameworks' assessments in the confidentiality line. Section 1 has one table: each piece of evidence once, in a fixed order, with the requirement of every chosen framework it answers and the sections behind it; the review timing rows (`approvals` and `interval`) of all frameworks share one row. Sections 3 to 9 are the same for any framework and are not repeated. One framework renders as before, with its own cover and checklist.

Data owner sign-off (Section 8.1): one row per folder set. The data owners are the members with `is_owner`, with their `title`. An approval is the data owner's when it is by a person (`actor.type` not `system`) and its `actor.name` matches a data owner's name, ignoring case and outer spaces, because approvals carry no email or ID. The folder set counts as approved by its data owner when the data owner's latest approval inside the period (not `carried_into_range`) did not end in the period. The row gives that approval's time in UTC and how it was made (`actor.surface`: "Polar Sky console" or "AI assistant", with `actor.assistant_client` in brackets). Every other folder set is shown as not approved by its data owner, with the reason: the data owner's approval was withdrawn, replaced or rejected; it was approved in the period only by other people (named) or only by Polar Sky; it had no approval in the period (with its last approval before it); no approval is recorded; or no data owner is recorded. A later approval by someone else is noted next to the data owner's. Section 1 (ISO 27001's "Reviewed by the owner of the information" row), the summary block and `--check` give the count and name the folder sets not approved by their data owner.

Who decided a member: `provenance.by` `system` is "Polar Sky" (it proposed the member; an approval of the folder set that included them is the decision); `user` is `provenance.by_name`. The date is `provenance.at`.

Account types (the PCI DSS "Vendor accounts included" row): `account_type` is shown as the provider gives it, the Microsoft 365 user type (`Member` or `Guest`) or the Google Workspace employee type. The row counts members by type, and says that the Microsoft 365 `Guest` members, with how many distinct accounts (by email) they are, are each listed in Attachment A with who decided their access and when; for Google Workspace it says the types are as Google Workspace gives them. The report never guesses a vendor from an email domain. With no account types, it says so plainly. A member with no account type shows "Not recorded" in Attachment A and is counted last, for example "Full time 4, not recorded 4".

Extract and members list: with a completed extract, Section 3.3 lists each person grant in the extract (`row_kind` `grant`, `grantee_type` `user`) that the members list of that folder set does not show, matched by email: the person is not a member, is a member and the grant has a role other than the member's `role` (shown alone), or the row has no email, so it cannot be matched (for example a shared drive Manager role, `organizer`, that every folder inherits). Section 3 says how many. Attachment B also lists each group the extract shows granting access (`grantee_type` `group`) that is not among the folder set's kept or dropped groups (by email when both have one, else by name), with the outcome "Found in the live read, not decided in Polar Sky" and its member count from the extract; a member reached through such a group (`group_member` rows, `via_group_name`) gets the group in "Through groups", marked "(live read)". An extract that read no folder gives no such list.

Extract names: a row with no `principal_name` (Google Workspace group member rows carry only `principal_email`) shows its `principal_email` in the "Person or group" column of `extract.csv`.

Reason: the member's `basis` if present, in words for the tags the import uses (`owner`, `predicted`, `group_expansion`, `existing_group_grant`, `direct_grant`, `service_account`); otherwise "Proposed by Polar Sky: " and the control's `reason` for a member Polar Sky proposed, and "Added or changed by " and the person's name for one a person decided.

The skill asks for `requested_by`, `procedure`, `removal_deadline`, `retention` and `acknowledgment` (and `review_interval` when a chosen framework has `needs_interval`: SOC 2, ISO 27001 and SOX); when one is missing the report shows TBD and the summary block lists it. `review_interval_months`, `review_interval_days` and `removal_deadline_days` never show TBD: without it, Section 6.2 "Within the deadline" says "Not available in this version". The fields step 2 of the skill marks optional (`control_owner`, `previous_review`, `data_source`, `exclusions`, `prepared_for`, `logo`) never show TBD: with no `control_owner`, `previous_review` or `exclusions` the report leaves its row out, `data_source` and `prepared_for` take their defaults, and with no logo the cover shows none.

Removal deadline check: only removals with `source` `removal_record` are checked; the report says nothing about the deadline for other removals. The decision date (`decided_on`) is the latest `approvals[].at` of the same folder set, including the approval carried into the period, at or before the removal's `at`. Days are calendar days in UTC between the two dates. An applied removal (`result` `removed`) is within the deadline when its days are at most `removal_deadline_days`, and over it otherwise; a failed or pending one is "not done by the period end", with the days from the decision to the last day of the period (or `generated_at`, when that is earlier), because the evidence covers the period only. A failed or pending record is "done later on <date>" instead, with the days from its decision to that date, when a later record on the same folder set with `result` `removed` has the same `action`, `target`, permission (`role`, `from_role`, `to_role`), grantee (`grantee_kind`, `email` or else `principal`) and `link_scope`, and is never linked when it does not identify the grantee (a person with no `email`, or no `principal`); the counts take that access once, by the later record, and "not done by the period end" counts only access no later record removed. Every record stays its own row. A record with no approval at or before it says so and is not counted. Section 6.2 and the removals line of the checklist give the counts, and 6.2 names the removals over the deadline (the first five; the rest are in Attachment D).

The logo: the render refuses a file that does not exist, is larger than 2 MB, does not end in `.png`, `.jpg`, `.jpeg` or `.svg`, or whose first bytes are not those of the type its name says (PNG and JPEG signatures; for SVG, an `<svg` element first, after an optional XML declaration, comments and SVG doctype). It puts the file into `report.html` as a `data:` URI in an `<img>` element, so the HTML and the PDF carry the logo with them and the render writes no other file. A browser shows an SVG in an `<img>` element as a picture only: it runs no script in it and loads nothing it links to, so the SVG is not changed or cleaned. The logo is scaled to fit a 1.7 by 0.6 inch box on the cover.

## Earlier answers

`scripts/previous_answers.py` keeps these fields from an earlier `inputs.json` the skill wrote: the text fields `organization`, `requested_by`, `procedure`, `removal_deadline`, `retention`, `review_interval`, `control_owner`, `data_source`, `exclusions`, `prepared_for` and `running_footer` (non-empty, up to 2,000 characters), `framework` (one of `frameworks.json`) or `frameworks` (a list of them, each once; the answer set is then listed under each of them in `by_framework`), `removal_deadline_days`, `review_interval_months` and `review_interval_days` (as the renderer reads them), `acknowledgment` `name`, `title` and `statement`, `columns` (the ids still in `columns.json`, per table; a table with none left is dropped), and `logo` while its file exists. Every other field, and any value of the wrong type, is dropped.

Next to the answers it prints `columns`, which says how the earlier report chose its columns: `last_time` is `defaults` when that report saved no columns (it kept the default columns) and `chosen` when it did; `changed_tables` lists the tables whose saved columns differ from today's defaults, in `columns.json` order; `no_longer_offered` holds, per table, the saved ids that `columns.json` no longer has; `defaults_not_in_last` holds, per saved table, today's default ids that the saved columns leave out (a column that became a default since, or one the person dropped).

It also prints `not_given_last_time`: the answers step 2 of the skill asks for that the earlier answer set lacks, in the order the skill asks them, each as `{"inputs": [...]}` with the input keys it fills (`acknowledgment.title` names `title` inside `acknowledgment`). The list draws on `organization`, `requested_by`, `procedure`, `retention`, `removal_deadline_days`, `review_interval_months` or `review_interval_days` (only when a framework of the answer set has `needs_interval`), and the acknowledgment `name`, `title` and `statement`; the wording of the removal deadline and the review interval is not listed when its number is there, since the report words the number itself. When the earlier `removal_deadline` or `review_interval` text states the number unambiguously, the item also has `suggestion` (the input key and the number, for example `{"review_interval_months": 6}`) and `read_from` (the text field it came from). A deadline is read only from a text that starts with one length in calendar days ("Within 30 days of the decision"); an interval only from a text that starts with one length in days, months or years ("Every 6 months", "Every 90 days") or with one of monthly, quarterly, semi-annually, half-yearly, annually or yearly. Two different lengths, any other number (a range such as "6-12 months", a version number), business or working days, weeks, hours, a number in words, a word with a prefix such as bi-annually or semi-monthly, or one of the words not, no, never, twice, thrice, times, unless, except or or give no suggestion. The skill asks the person to confirm a suggestion before it uses it.

## Output

`report.html`, `fonts/`, and one CSV per table: `members.csv`, `groups.csv`, `shares.csv`, `removals.csv`, `approvals.csv`, and `extract.csv` when there is a completed extract. `extract.csv` holds the extract's rows in the stored file's order; it is a rendering of the stored file, so its SHA-256 differs from the stored file's, and Attachment F lists both. CSV files are UTF-8 without a byte order mark, CRLF line ends, quoted only where needed (RFC 4180), and use the column ids as the header. A cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a single quote in front, so a spreadsheet does not run it as a formula (OWASP CSV injection guidance); the HTML shows the value unchanged. Members are labeled as at report time, not as at the end of the period, because `list_control_members` returns the members a control has now: the `as_of` column in `members.csv` and the member headings in the HTML carry the extract's `as_of` when there is a completed extract; otherwise, for a data folder, the time the last `list_control_members` file in `responses/` was saved (its modification time), so a later render keeps the read time; and for a single data file, `generated_at`. Kept direct shares carry, in the `read_at` column, the `kept_direct_shares_as_of` of the evidence response they were last read from. The chosen columns also set the HTML tables for groups, kept direct shares and removals. `make_pdf.py` adds `report.pdf`; a render removes the `report.pdf` an earlier render left, so an old PDF never sits next to a new HTML report.
